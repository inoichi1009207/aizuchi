# 已知问题与欠件(2026-08-28)

每条都带**观测证据**与**当前处置**。没有证据的猜测不进这份文件。

## 1. 本部署中改 `webui.json` 的 `host` 后 6099 监听地址未变(机制未明)

**观测**:
- `webui.json` 里 `host` 已设为 `127.0.0.1`(文件改于 10:26:02)
- NapCat 进程于 12:55:39 启动 —— **晚于**配置变更 2.5 小时
- `netstat` 实测 6099 仍为 `0.0.0.0` 与 `[::]`

⚠️ **更正(2026-08-28 外审)**:原文写「NapCat 读了该字段但不按它绑定」——**不成立**。
上游源码把 `parsedConfig.host` 一路传到 `server.listen(port, host)`,它是管这件事的。
更可能的原因是版本差异、**改的不是实际被加载的那个配置文件**、或启动参数覆盖 ——
这三者一个都没排除,就写了一句对第三方项目的否定判断。
未证明的部署现象不该写成别人项目的缺陷。复核前先确认 NapCat 版本与配置文件实际加载路径。

**当前处置**:靠 Windows 防火墙兜底 —— 三个配置档均为 `BlockInbound,AllowOutbound`,
且无 6099 的放行规则(已实测)。

⚠️ **这道防护是单点的**:防火墙规则一改、或云厂商安全组放开,6099 立刻暴露在公网。
WebUI 的 token 是**固定共享密钥**,拿到它 + 能连上 6099 即可控制机器人。
**未做**:显式加一条 Windows 防火墙拒绝规则(纵深防御)。

## 9. 两个独立审计者同时查出:被 @ 路径此前完全不过闸(2026-08-28,已修)

**观测**:`grep -n "limiter\." plugin/main.py` 当时只有三处命中,全在主动分支。
被 @ 分支只查一个进程内、按 `(gid, uid)` 分键的 10 秒冷却 —— 不落盘、重启即失、
十个人轮流 @ 即每秒一张。

**为什么它没被发现**:**没有任何测试 import 过 `main.py`**。四个测试文件全部只构造
`FloodLimiter`,于是「被 @ 分支根本不调用它」这件事没有任何断言能看见。
同一原因让此前那个 gate/commit 竞态也逃过了回放测试。

**量级**:当日实测被 @ 发送 17 次 / 主动发送 6 次 ⇒ `cap_per_24h` 这道
「防止把小号打进风控(不可逆)」的闸,当时管的是 **26%** 的流量。

**已修**:`limiter.allow_mention()`,与主动路径**共用 `cap_per_24h`**,
另加 `mention_floor_sec`(缺省 3 秒)防多人轮流。刻意不套 `min_interval` 也不掷骰
——有人直接叫你就该回应。回放测试新增断言⑦⑧覆盖它。

**未修的同族**:测试仍然不 import `main.py`,所以 handler 层的接线仍无断言保护。

## 10. 回放测试的断言②曾从被测模块导入自己的标尺(2026-08-28,已修)

**观测**:`tests/test_replay.py` 原本 `from limiter import FloodLimiter, WINDOW_SEC`,
而断言②用 `WINDOW_SEC` 去量「任意 24h 窗口内的发送数」。两边一起动。

**变异实证**:把 `limiter.WINDOW_SEC` 改成 24 分钟,三天发送量从 45 涨到 **618**
(14 倍刷屏回归),**四个测试文件全部通过,退出码 0**。修复后同一变异体当场被断言②打死。

**教训**:断言的标尺必须由测试自己拥有。名字里写着「24 小时」的断言,
就该由测试写死 86400,而不是问实现「你现在觉得 24 小时是多少」。
