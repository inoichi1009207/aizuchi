# aizuchi

一个只会发表情包的 QQ 群机器人。

它不说话。被 @ 时，以及偶尔在群里氛围合适时，它从你自己的表情包池里挑一张贴出来——仅此而已。

```
你：@机器人
它：[一张星星眼的表情包]
```

没有文字，没有解释，没有「作为一个 AI 助手」。

---

## 为什么不让它说话

这不是偷懒，是整个设计的支点。

**约束就是产品。** 一个「会聊天、顺便发表情」的机器人是第一万零一个 LLM 群聊 bot。一个**只能从十几张脸里挑一张**的机器人是另一种东西。

具体好处有四条，每条都实在：

**输出空间是封闭的。** 它只能发出池子里的某一张图，所以提示词注入拿不到任意输出——但注意这**降低**的是可见输出的风险，不是消除全部风险：诱导它挑一张冒犯性的图、骗它反复发图消耗额度，这些依然做得到。有人试图调戏它，它回一张表情——那本身就是包袱。项目也**不提供任何聊天内命令**，因为那是唯一会把任意文本送进特权路径的口子。

**失败模式变好了。** LLM 生成的中文闲聊容易啰嗦、油腻或答非所问，而且错得一眼可辨。表情贴歪了顶多是好笑，不尴尬。你把一个「会翻车」的输出空间，换成了一个「翻车也能加分」的输出空间。

**十几张够用，恰恰因为没有文字。** 有文字时人会严格审判相关性；只有表情时，歧义由群友自己脑补填平。这是表情包在人类群聊里本来就成立的机制。

**输出侧成本很低。** 每次回复的输出只有几个 token。但总成本取决于输入侧——上下文条数、描述表长度、调用频率与 provider 定价，这几项本项目**没有实测账单**，别把「输出短」当成「便宜」。

## 它长什么样

**被 @ 时**：从池子里挑一张回。同一个人在冷却时间内重复 @，只回第一次；
**并且计入全局 24h 总量**（`cap_per_24h`），两次发送之间还有一个几秒的全局下限。

> ⚠️ 早期版本里这条路径**完全不过闸**——只有一个按人计的内存冷却，重启即失。
> 十个人轮流 @ 就是每秒一张，而配置里那句「失控刷屏可能把小号打进风控，那是不可逆的」
> 写在一个管不到它的参数上面。2026-08-28 由两个独立审计者各自查出并修复。

**没被 @ 时**：偶尔自己冒个泡。这条路要过三道闸——硬冷却、日配额（与被 @ 共用）、掷骰——**闸全过之后还要问模型「此刻该不该插话」**，模型可以说不。三道闸都在调用模型**之前**，所以冷却期内不产生任何 API 费用。

模型收到的两种场景提示词是**不一样的**：

- 被 @：「有人在直接叫你，除非实在没合适的，否则应当回应」
- 主动：「没有人叫你。你是这个群里的一员，不是需要被批准才能说话的客人。闲聊时接话是正常的；但**讨论正事、有人真难过、刚贴过、纯刷存在感 → 弃权**」

这个区分是有代价换来的——早期版本两种场景用同一套提示词，模型根本不知道自己在做「要不要插嘴」这个决定。

## 不分发素材

**仓库里没有任何表情包图片。** `stickers/` 被 gitignore，你自备。

这不只是版权顾虑，也是更好的架构：一个硬编码十几张特定图片的机器人是个人玩具；一个**吃你自己那个表情包文件夹**的机器人是别人能用的工具。

### 版权边界

如果你的表情包是从别人的作品里截的（多数人都是），那么：

- **私人群聊里用**：整个中文表情包文化都建立在这上面，实践中鲜见追究——但这是观察到的现状，不是法律结论。是否构成合理使用取决于作品、来源、传播范围与使用方式，本项目不提供任何法律保证
- **把图片提交进公开仓库**：这是**再分发**，性质完全不同，风险是真的

所以这个项目把代码和素材分开。你在自己机器上用什么图是你的事，仓库不参与。

## 描述表：整个项目质量的真正来源

**模型看不到图，它只看得到你写的文字。** 所以 `stickers/stickers.yaml` 是这个机器人的灵魂，不是配置文件。

```yaml
pool_note: |
  写清楚你的池子**缺**哪类情绪 —— 模型才知道什么时候该弃权。

stickers:
  - file: xxx.jpg
    mood: 蔫了                       # 主读法
    also: [共情陪伴, 累, 被打击]      # 其他成立的读法
    desc: 眼睑下垂,趴在课桌上,没精神。 # 客观描述画面
    use_when: 自己没劲;或对别人共情    # 什么语境下用它
```

三条经验，都是踩出来的：

**一张图不止一个意思。** `also` 字段存在的理由：曾经把「蔫了」钉死成「自己没精神」，于是砍掉了它最有用的用法——对着别人的倒霉事表示「我也替你难过」。写窄了等于替模型提前砍掉选项。

**`pool_note` 要写你缺什么。** 模型不知道你池子里没有「生气」，它会拿最接近的硬凑。明确告诉它「需要表达愤怒时请弃权」，比多加十条描述有用。

**让将来挑图的那个模型自己写描述。** `tools/describe_stickers.py` 用视觉模型看图生成描述表初稿。运行时挑图的是谁，描述就该由谁写——换个模型来描述，等于让 A 写说明书给 B 用。

## 安装

需要 [AstrBot](https://github.com/AstrBotDevs/AstrBot) + 一个 OneBot v11 协议端（如 NapCat）。

1. 把 `plugin/` 放进 AstrBot 的 `data/plugins/aizuchi/`
2. `config.example.yaml` → `config.yaml`，填好群号
3. 表情包放进 `stickers/`，照 `stickers.example.yaml` 写描述表
4. 重启 AstrBot

跑通前自检：

```bash
python tests/test_replay.py               # 防刷屏闸,退出码 0 = 全绿
python tests/probe_rate1_determinism.py   # 骰子确实接在决策路径上
python tests/probe_mutation.py            # 上一个测试的盲区被补上了
python tests/probe_race.py                # 并发下硬冷却不会被绕过
python tests/probe_corrupt_state.py       # 状态文件坏了不打死插件、也不静默归零
git ls-files | grep -iE '\.(jpg|jpeg|png|gif|webp)$'   # 必须无输出:素材不入库
```

⚠️ Windows 上部署时若日志刷 `UnicodeEncodeError: 'gbk' codec`，那是控制台编码问题，**会丢日志行**，排障前先设 `PYTHONIOENCODING=utf-8`。

## 配置

```yaml
llm:
  model: deepseek-v4-flash-vision-exp   # 留空则用 AstrBot 默认 provider
                                        # 本插件不持有 API key,走 AstrBot 已配好的 provider

vision:
  max_images: 3        # 每次带几张群里最近的图。0 = 纯文字模式

mention:
  per_user_cooldown_sec: 10   # 同一人重复 @ 的冷却

proactive:
  rate: 0.3            # 掷骰命中率:控制模型被咨询的频率
  min_interval_sec: 60 # 硬冷却:只防连珠炮
  cap_per_24h: 150     # 滚动 24h 上限。写 0 = 不限(你关掉的是最后一道防线)
  context_window: 20   # 给模型看的最近消息条数
  adaptive:            # 自适应节奏:按「自己的占比 vs 公平份额」调整积极性
    enable: true
    window_sec: 600    # 观察窗口
    boost: 2.0         # 说得少于公平份额时的倍率
    suppress: 0.3      # 说得多于公平份额时的倍率

groups: []             # 只在这些群生效。**留空 = 一个群都不响应**(fail-closed)
                       # 早期版本留空等于「全部群」,漏配就会在所有群里冒泡 —— 已改
ignore_sender_ids: []  # 其他机器人的 QQ 号,防回声循环
```

**调参提示（实测，非推测）**：在活跃群里，`cap_per_24h` 是**唯一**的总量闸。固定 cap 时 `rate` 从 0.01 扫到 1.0，三天总量一次不变；而只动 cap，总量完全线性。`rate` 管的是节奏自然度，不是总量。

## 同类项目与方法论定位

「只发表情包的群机器人」这个品类本身很小，所以下面比的不是功能表，是**方法**。

### 最近的邻居

[`sticker-reply-skill`](https://github.com/Zhanglala103838/sticker-reply-skill) 是**本次公开检索范围内**功能最相近的项目之一：
让 AI 助手基于情绪检测、上下文感知和反馈学习来选表情包回复。思路相通，
差别在于它是给助手**增加**一种表达方式，而本项目是**只保留**这一种——
封闭输出空间是这里的支点，不是附加功能。

更常见的一类是通用 LLM 群机器人框架（[LangBot](https://github.com/RockChinQ/LangBot)、
[Gensokyo-llm](https://github.com/Hoshinonyaruko/Gensokyo-llm) 等）。
它们解决的是「怎么把大模型接进聊天平台」，本项目解决的是「接进来之后什么时候该闭嘴」——
不同层的问题。本项目本身就跑在 AstrBot 上，属于这类框架的下游。

### 学界怎么看「什么时候该沉默」

这个问题有正经研究：

- CHI EA '26 的 [Read the Room](https://dl.acm.org/doi/10.1145/3772363.3798392)
  （extended abstract，约 6 页）研究群聊中 LLM agent 何时参与、何时保持沉默。
  标题、作者、DOI、会议归属已核实；**但全文取页失败**——
  本项目设计时借鉴的是「沉默也需要被设计」这个问题意识，
  至于论文的具体发现，我没能读到全文，因此**不在此转述**。
- ⚠️ 更重要的是：该研究对象是混合语境群聊里的通用 LLM agent，
  与本项目（表情包单输出 + 静态硬闸）在输出形式和限流机制上都不同。
  **它启发了这里的设计，但没有验证这里的效果。** 别把「方向相似」读成「有实证背书」。

### 研究指出的一个缺口,以及本项目怎么补的

有研究采用**动态限流**：按 agent 的发言频率相对活跃参与者的比例调整
——低于 1/n 时鼓励多说，高于时转为倾听者。

本项目**最初只有静态闸**（固定冷却 + 固定配额 + 固定骰子率），
不会因为群里今天特别热闹或特别冷清而变。这是个真缺口，
而且当时的托词是「静态可被回放测试机械验证，动态更聪明但更难验证」——
**那个二选一是假的**：同一套回放台架照样能验动态策略。

现已实现（`limiter.py` 的 `observe()` + `_effective_rate()`）：
按「自己的发言占比 vs 公平份额 `1/(人数+1)`」调整骰子率。实测（2 小时模拟，每 10 秒一条）：

| | 2 人群 | 12 人群 |
|---|---|---|
| 静态 | 46 次 | 46 次 |
| 自适应 | 72 次 | 53 次 |

人少时放开、人多时收敛，静态闸做不到这件事。

**硬闸永远先过，自适应只影响骰子**——算错也突破不了冷却与日配额这两条物理上限。
配置项 `proactive.adaptive`，可单独关闭以退回静态行为（关闭时回归测试逐条通过，
行为与实现前完全一致）。

### 方法论上真正不同的三点

1. **封闭输出空间当作安全边界**，而不是功能限制。可见输出的注入面被压到「池子里的某一张图」，是这个设计的副产品，不是额外加的防护——但注入面被**压小**不等于**归零**。
2. **弃权是一等公民。** 模型被明确告知「沉默是默认答案」，且弃权时**不消耗冷却**——
   下一条消息还能再判断一次。多数 bot 的设计里，「不回答」是失败路径。
3. **闸在调用模型之前。** 冷却期内根本不问模型，成本为零。
   常见的反向写法（先问模型再决定发不发）会让 API 账单与群活跃度成正比，而防刷屏效果一样。
